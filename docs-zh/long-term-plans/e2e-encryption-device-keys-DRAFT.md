# SuperSync 的渐进式端到端加密 — 修订版方案

> **状态：已归档 — 已否决**
>
> 因 4 个关键阻塞问题被否决。详见 `e2e-encryption-CRITICAL-ISSUES.md`。已实现方案采用基于密码的加密 — 参见 `../sync-and-op-log/supersync-encryption-architecture.md`。

## 执行摘要

**原始方案已被否决**，综合智能体审查后发现致命缺陷：

- 基于令牌派生的加密在 7 天令牌过期后失效
- 多设备同步不可行（每台设备的令牌不同）
- 行业共识：没有生产系统使用认证令牌进行加密

**新方案：** 设备生成主密钥，附带可选的云备份（WhatsApp 模型）

## 研究摘要（3 个深度探索智能体）

### 智能体 1：端到端加密模式研究

- **发现：** 所有主流端到端加密系统（WhatsApp、Signal、1Password）都使用设备生成的随机密钥
- **原因：** 认证令牌是临时的，加密密钥必须是永久的
- **建议：** 采用 WhatsApp 2021 年云备份模型（20 亿+用户，大规模验证）

### 智能体 2：JWT/令牌加密研究

- **发现：** 基于令牌派生的加密是一种安全反模式
- **原因：** OAuth 令牌必须轮换以保障安全，这会破坏加密
- **建议：** 将认证（OAuth）与加密（设备密钥）分离

### 智能体 3：SuperSync 令牌分析

- **发现：** 令牌 7 天后过期，不存在自动刷新机制
- **当前行为：** 用户每 7 天后重新登录
- **风险：** 添加适当的令牌轮换（安全最佳实践）会破坏基于令牌派生的加密

## 目标

- ✅ 为所有 SuperSync 用户默认启用端到端加密
- ✅ 单设备用户零密码（密钥自动生成）
- ✅ 谨慎用户可选的恢复机制（云加密备份）
- ✅ 多设备支持（QR 码配对或恢复密码）
- ✅ 保持强安全性（256 位随机密钥，非密码派生）

## 架构：设备生成密钥 + 可选云备份

### 安全模型

**密钥生成：**

- 每台设备通过 WebCrypto API 生成随机 256 位 AES-GCM 密钥
- 以不可提取密钥形式存储在 IndexedDB 中（受 XSS 保护）
- 除非用户启用云备份，密钥从不离开设备

**可选云备份：**

- 用户在设置时设置恢复密码（强烈建议）
- 通过 Argon2id 从密码派生密钥加密密钥（KEK）（内存硬、抗 GPU）
- 主密钥用 KEK 加密后上传到 SuperSync 服务器
- 服务器无法解密（密码从不传输）

**多设备同步：**

- **方案 A：** QR 码配对（主设备 → 新设备）
- **方案 B：** 恢复密码（从云端下载加密密钥）

### 用户流程

#### 首次设置（新用户）

```
1. 用户启用 SuperSync → 输入访问令牌
2. 应用生成随机 256 位加密密钥
3. 密钥存储在 IndexedDB 中（通过 WebCrypto 设为不可提取）
4. 弹出对话框：
   ┌─────────────────────────────────────────────────┐
   │ 🔒 加密已启用                                    │
   ├─────────────────────────────────────────────────┤
   │ 您的数据现已使用安全密钥加密。                     │
   │                                                  │
   │ ⚠️  设置恢复密码，以防止清除浏览器时               │
   │    数据丢失。                                    │
   │                                                  │
   │ 恢复密码：[.....................]                  │
   │ 确认密码：[.....................]                  │
   │                                                  │
   │ [跳过（不推荐）]  [设置密码]                      │
   └─────────────────────────────────────────────────┘

5a. 如果用户设置了密码：
    - 使用 Argon2id 从密码派生 KEK
    - 用 KEK 加密主密钥
    - 将加密后的密钥上传到服务器
    - 显示："✓ 恢复已启用。请保存此密码！"

5b. 如果用户跳过：
    - 显示严重警告：
      ┌─────────────────────────────────────────────┐
      │ ⚠️  警告：无法恢复                            │
      ├─────────────────────────────────────────────┤
      │ 如果清除浏览器或丢失此设备，                   │
      │ 所有数据将永久丢失。无法恢复。                  │
      │                                              │
      │ 您确定吗？                                    │
      │                                              │
      │ [取消 — 设置恢复密码]  [我确定，继续]          │
      └─────────────────────────────────────────────┘
```

#### 正常启动

```
1. 应用加载
2. 从 IndexedDB 加载加密密钥
3a. 如果密钥存在：继续正常操作
3b. 如果密钥丢失：
    ┌─────────────────────────────────────────────┐
    │ 🔑 加密密钥丢失                               │
    ├─────────────────────────────────────────────┤
    │ 未找到本地加密密钥。                           │
    │                                              │
    │ [输入恢复密码]  [从另一台设备扫码]  [擦除数据] │
    └─────────────────────────────────────────────┘
            │                        │
            ▼                        ▼
    从服务器下载加密密钥     显示 QR 码扫描器
    用密码解密              扫描主设备上的码
    密钥存储在 IndexedDB    共享密钥通过端到端加密
    继续正常操作            通道传输
                            密钥存储在 IndexedDB
                            继续正常操作
```

#### 添加新设备

**方法 1：QR 码配对（推荐，离线）**

```
1. 在主设备上：设置 → 加密 → 配对设备
2. 主设备生成一次性 QR 码（包含加密的密钥材料）
3. 在新设备上：设置 → 加密 → 扫描配对码
4. 新设备扫描 QR 码
5. 密钥通过安全通道传输
6. 新设备将密钥存储在 IndexedDB 中
7. 新设备开始同步加密数据 ✅
```

**方法 2：恢复密码（在线）**

```
1. 在新设备上：设置 → 加密 → 使用恢复密码
2. 新设备请求加密的密钥包
3. 下载加密的密钥
4. 提示输入恢复密码
5. 在本地解密密钥
6. 密钥存储在 IndexedDB 中
7. 开始同步 ✅
```

### 数据结构

```typescript
// 存储在服务器上（加密）
interface EncryptedKeyBackup {
  encryptedKey: string;      // 用 KEK 加密的 AES-GCM 密钥
  salt: string;              // Argon2id 盐值
  iv: string;                // AES-GCM 初始化向量
  createdAt: string;         // ISO 时间戳
  keyPairId: string;         // 用于配对操作的密钥对标识符
}

// 本地存储（IndexedDB，不可提取）
interface LocalKeyStore {
  key: CryptoKey;            // WebCrypto 密钥对象（不可提取）
  keyPairId: string;         // 服务器上的匹配标识符
  hasCloudBackup: boolean;   // 是否有恢复密码备份
}
```

### API 端点

```typescript
POST /api/v1/e2e-keys/backup
  Body: { encryptedKey: string, salt: string, iv: string }
  Auth: SuperSync 访问令牌
  描述：存储加密的密钥包用于恢复

GET /api/v1/e2e-keys/backup
  Auth: SuperSync 访问令牌
  响应：{ encryptedKey, salt, iv, createdAt }
  描述：获取用户的加密密钥包

GET /api/v1/e2e-keys/pairing-challenge
  Auth: SuperSync 访问令牌
  响应：{ challenge: string, expiresAt: string }
  描述：获取 QR 码配对挑战

POST /api/v1/e2e-keys/pairing-response
  Body: { challengeId: string, encryptedKey: string }
  Auth: SuperSync 访问令牌
  描述：响应配对挑战并交换密钥
```

## 安全考量

### 威胁模型

**攻击者能力：**

- 服务器被攻破（可读取数据库）
- 网络窃听（中间人攻击）
- XSS 攻击（恶意 JavaScript）
- 物理设备被盗

**安全保障：**

| 攻击类型          | 无恢复模式                    | 有恢复密码                          |
| ----------------- | --------------------------- | ----------------------------------- |
| 服务器被攻破      | ✅ 数据已加密                 | ✅ 数据已加密（KEK 不在服务器上）     |
| 网络中间人攻击    | ✅ TLS 保护密钥上传           | ✅ TLS 保护加密密钥                  |
| XSS 攻击          | ⚠️ 可调用加密/解密            | ⚠️ 可调用加密/解密                   |
| 设备被盗          | ❌ 密钥在 IndexedDB 中        | ❌ 密钥在 IndexedDB 中               |
| 浏览器清除        | ❌ 数据丢失                   | ✅ 可通过密码恢复                    |

**非目标（范围外）：**

- 硬件支持的密钥存储（需要平台特定代码）
- 防止浏览器内存利用（Spectre 等）
- 完美前向保密（单个主密钥重复使用）

### 隐私考量

**服务器知道的内容：**

- 用户已启用端到端加密
- 用户有云备份（如果启用）
- 同步操作数量（元数据）

**服务器无法知道的内容：**

- 主加密密钥（从不传输）
- 恢复密码（从不传输）
- 解密后的操作内容

## 风险与缓解措施

**风险：** 用户忘记恢复密码

- **缓解措施：** 密码强度计、明确警告、建议使用密码管理器

**风险：** 浏览器兼容性问题

- **缓解措施：** WebCrypto 在所有现代浏览器中受支持，针对老旧浏览器回退到传统模式

**风险：** 浏览器激进清理导致 IndexedDB 被清除

- **缓解措施：** 检测密钥丢失、显示恢复对话框、引导用户使用恢复密码

**风险：** QR 配对安全问题

- **缓解措施：** QR 码 5 分钟后过期，使用临时密钥加密

## 与原始方案对比

| 方面                | 原始方案（令牌派生）          | 修订方案（设备密钥）           |
| ------------------- | --------------------------- | ----------------------------- |
| 密码负担            | 零                          | 零（可选）                     |
| 安全性              | 弱（令牌 = 密钥）            | 强（随机密钥）                  |
| 多设备              | 不可用                      | 可用（QR/恢复）                |
| 令牌轮换            | 破坏加密                    | 无影响                         |
| 行业采用            | 零系统                      | 所有主流端到端加密应用           |
| 实施工作量          | 6-8 周                      | 12 周                          |
| 恢复选项            | 无                          | 云备份 + QR                    |

## 建议

**按修订方案推进。** 设备生成密钥加可选云备份是端到端加密的行业标准方法，密码负担最小。

额外的 4-6 周实施时间由以下理由证明合理：

- 稳健的安全模型（令牌轮换不会破坏加密）
- 在大规模下得到验证（WhatsApp、Signal）
- 更好的用户体验（恢复选项）
- 面向未来的架构
