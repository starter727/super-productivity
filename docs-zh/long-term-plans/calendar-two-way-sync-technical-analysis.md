# 实现真正双向日历同步的技术挑战

> **状态：已计划**

## 执行摘要

基于我对 Super Productivity 代码库的探索，实现真正的双向日历同步面临若干重大的技术挑战，这些挑战超出了已存在的稳健同步基础设施的范围。虽然应用对其自有数据具有基于操作日志的复杂同步和只读 iCal 轮询功能，但桥接这些系统以实现双向日历同步需要解决认证、API 集成、冲突解决和架构方面的挑战。

---

## 当前状态评估

### 已有功能 ✓

1. **只读 iCal 集成** - 以可配置的间隔轮询 HTTP/HTTPS iCal 源
2. **稳健的内部同步** - 具有用于冲突检测的向量时钟的操作日志
3. **任务转换** - 单向：日历事件 → Super Productivity 任务
4. **重复事件处理** - 完整的 RFC 5545 iCalendar 解析，支持 RRULE

### 缺失功能 ✗

1. **OAuth2 认证** - 无直接的 Google Calendar/Outlook API 集成
2. **写操作** - 无法在外部日历中创建/更新/删除事件
3. **双向映射** - 无反向映射：任务 → 日历事件
4. **Webhook/推送通知** - 仅轮询架构（无来自日历的实时更新）

---

## 技术挑战分解

### 1. 认证与授权 🔴 **关键**

**挑战：** 外部日历 API 需要 OAuth2 认证，且各平台实现不同。

**当前状态：**

- iCal 集成使用匿名 HTTP 获取（无认证）
- 代码库中无 OAuth 流程实现
- Electron + PWA 环境需要不同的认证策略

**所需工作：**

- **Google Calendar API：**
  - 具有离线访问 + 刷新令牌的 OAuth2
  - 范围：calendar.events（读/写）
  - 令牌存储在加密配置中
  - 刷新令牌轮换处理
  - 多账号支持（工作 + 个人日历）

- **Microsoft Outlook/Office 365：**
  - Microsoft 身份平台 OAuth
  - 与 Google 不同的端点结构
  - 需要 Azure AD 应用注册

- **跨平台考虑：**
  - **Electron 桌面：** 可使用本地 Web 服务器回调进行 OAuth
  - **PWA/Web：** 必须使用基于重定向的 OAuth 流程
  - **移动端（Capacitor）：** 用于 OAuth 重定向的深度链接
  - **基于文件的同步：** 如何在设备间安全同步 OAuth 令牌？

**复杂度：** 🔴 **高** - 每个提供者需要自定义实现，令牌安全至关重要

---

### 2. 双向数据映射与同步 🔴 **关键**

**挑战：** 将 Super Productivity 任务映射到日历事件，两者数据模型不同。

**当前状态：**

- 仅单向：CalendarIntegrationEvent → Task（通过手动/自动导入）
- 无反向追踪：无法知道哪个任务来源于哪个日历事件
- 无任务到事件的转换逻辑

**所需工作：**

#### A. 实体关系模型

`
Task → CalendarEventBinding {
  taskId: string;
  calendarEventId: string;          // 外部日历的事件 ID
  calendarProviderId: string;       // 哪个日历（Google/Outlook/iCal）
  calendarId: string;               // 提供者中的哪个特定日历
  isBidirectional: boolean;         // 这是双向同步的事件吗？
  lastSyncedAt: number;             // 防止同步循环
  syncDirection: 'to-calendar' | 'from-calendar' | 'both';
}
`

#### B. 字段映射挑战

| Super Productivity | 日历事件         | 冲突可能性                             |
| ------------------ | ---------------- | -------------------------------------- |
| 	itle            | summary        | ✓ 低                                    |
| 
otes            | description    | ✓ 中——格式差异                          |
| dueDay（日期）    | start（日期时间）| 🔴 **高**——全天 vs 定时                 |
| 	imeEstimate     | duration       | 🔴 **高**——SP 估算 vs 固定时长          |
| isDone           | 无对应字段       | 🟡 中——可用参与者状态？                  |
| 	agIds[]         | categories[]?  | 🟡 中——支持有限                         |
| projectId        | 哪个日历？       | 🔴 **高**——SP 项目 ≠ 日历               |
| subTasks[]       | 无对应字段       | 🔴 **高**——无法同步嵌套结构               |
| epeatCfgId      | RRULE            | 🔴 **高**——不同的重复模型                 |
| emindCfg        | 提醒             | ✓ 低                                    |

**关键架构问题：**

> 任务和日历事件应该是**带有绑定的独立实体**（当前方法可扩展）
> 还是应该是**具有多个视图的统一实体**？

当前架构建议使用带有绑定的独立实体，但这为维护一致性关系增加了复杂度。统一实体方法（如 Notion 的数据库/日历视图）更简单，但对 SP 的任务系统的更改更大。

**复杂度：** 🔴 **高**——需要新的实体绑定和字段级冲突策略

## 结论：实现路线图

鉴于这些技术挑战的深度，以下是一个务实的分阶段方案：

### 阶段 1：只读增强（2-3 周）

- ✓ 改进当前 iCal 集成 UI
- ✓ 添加任务绑定追踪
- ✓ 在导入的任务上显示日历图标
- ✓ "在日历中查看"链接

### 阶段 2：单向导出（6-8 周）

- 实现 Google OAuth（Electron + Web + 移动端）
- 添加"导出到日历"操作
- 从任务创建事件（简单映射）
- 处理更新传播（任务 → 事件）
- 无需冲突解决（单向）

### 阶段 3：双向同步（12-16 周）

- 实现变更检测（状态哈希）
- 添加冲突解决（LWW + 手动）
- 支持简单重复事件
- 为离线操作添加同步队列
- 实现增量同步（syncToken）
- 添加全面测试

### 可选的未来阶段：

- Outlook/Office 365 提供者
- 复杂重复事件支持（主事件 + 例外）
- Webhook 支持（SuperSync 可用时）
- 子任务扁平化/嵌入
- 高级项目-日历映射

**置信度：** 75% - 架构合理，SP 现有的同步基础设施提供了坚实的基础。主要风险是重复事件（最难的问题）和跨平台的 OAuth 令牌管理。建议在承诺完整的双向同步之前，先为阶段 2 构建原型。
