# Operation Log 同步服务最佳实践

本文总结了基于操作日志（事件溯源）架构设计与实现离线优先同步服务的业界最佳实践。

## 1. 核心架构原则

### 1.1 事件溯源（真相是日志）

系统不直接修改当前状态，而是把每次变更记录为不可变事件（operation）。

- **收益：** 提供完整审计轨迹、支持时间回溯调试，并可从同一份数据构建不同状态投影（projection）。
- **最佳实践：** 服务端首要职责是按严格线性顺序持久化日志；“当前状态”只是日志推导结果。

### 1.2 中心化串行化（星型拓扑）

在客户端-服务端模型中，服务端是线性化点。

- **逻辑时钟：** 服务端为每个被接受的操作分配严格单调递增的 **Sequence Number**（或全局修订号）。
- **排序：** 该序号定义事件绝对顺序。若两个客户端同时上报，服务端可任意先后处理：第一个得 `Seq N`，第二个得 `Seq N+1`。
- **简化：** 全局排序不必依赖网状拓扑下复杂向量时钟；尽管客户端仍可用向量时钟管理本地分支。

### 1.3 服务端“笨”，客户端“聪明”

对于端到端加密或领域规则复杂的应用，服务端最好把 payload 当作不透明数据（或仅做最小校验）。

- **冲突解决：** 逻辑放在客户端。客户端下载新操作后，把本地 pending 操作 rebase 到其上（类似 `git rebase`）。
- **校验边界：** 服务端校验认证、授权和 schema 结构；通常不承载依赖客户端状态的业务规则。

## 2. 存储与数据库选择

### 2.1 SQLite vs PostgreSQL

| 特性         | SQLite               | PostgreSQL             |
| :----------- | :------------------- | :--------------------- |
| **适用场景** | 个人、自托管、嵌入式 | 多租户、企业级、高并发 |
| **并发能力** | 单写者（WAL 可改善） | MVCC（多版本并发控制） |
| **运维成本** | 近乎零（单文件）     | 中等（需服务管理）     |

- **建议：** 对个人效率工具（如 Super Productivity），自托管默认优先 **SQLite**。但数据访问层建议用查询构建器（如 Kysely、Knex）以支持未来切换 **PostgreSQL**（大规模部署或托管服务）。

### 2.2 不可变日志存储

- **仅追加：** `operations` 表应在语义上保持 append-only。
- **幂等键：** 用客户端生成 UUID（推荐 v7，利于按时间排序）作为主键，防止网络重试导致重复处理。

### 2.3 Tombstone（删除墓碑）

- **删除语义：** 离线优先系统里不能直接 `DELETE` 行，否则其他设备不会知道该项已删除。
- **实现：** 建 `tombstones` 表，或定义专门 `DEL` 操作类型。
- **清理：** 采用 TTL（如 90 天），超过同步视界（horizon）后再物理删除。

## 3. 同步协议

### 3.1 Push-Pull 循环

1.  **Push：** 客户端发送一批 `pending` 操作。
    - _Payload:_ `[Op1, Op2]`, `lastKnownServerSeq: 100`。
2.  **服务端处理：**
    - 检查严格单调序。
    - 分配新 `serverSeq`（101、102）。
    - 存储操作。
    - _冲突检测：_ 若 `lastKnownServerSeq` < `CurrentServerSeq`（如 105），服务端可选择拒绝（乐观锁）或接受后交给客户端后续合并（最终一致）。对“笨服务端”模式，后者通常带来更平滑的用户体验。
3.  **Pull：** 客户端请求“`serverSeq: 100` 之后所有操作”。
4.  **Ack：** 客户端确认已处理到 `serverSeq: 102`。

### 3.2 批处理与压缩

- **批处理：** 总是成批发送操作，HTTP/WS 建连开销较高。
- **压缩：** HTTP 响应用 `gzip` 或 `Brotli`。若 JSON 过于冗长，可考虑二进制格式（Protobuf/MsgPack），或直接压缩 JSON blob。

### 3.3 快照（冷启动加速）

回放 100,000 条操作来构建初始状态会非常慢。

- **快照：** 定期（如每 1,000 条操作）生成全量状态快照。
- **混合同步：** 新设备先下载最新 Snapshot，再拉取该快照之后的操作。

## 4. 客户端优化：合并与批量

### 4.1 写合并（Coalescing / Squashing）

写合并是指在同步前，将同一实体的多次细粒度更新合成一次操作。

- **适用场景：**
  - **快速文本输入：** 用户输入 “Hello”（5 次 op），可在防抖（如 500ms）后压成 1 次 op（"Hello"）。
  - **滑块/拖拽：** 拖动进度从 0% 到 50%，通常只关心最终值 50%。
- **收益：**
  - 减缓服务端日志增长。
  - 加快其他客户端回放/初始同步。
  - 降低网络开销。
- **风险：**
  - **历史损失：** 丢失中间按键级审计（通常可接受）。
  - **冲突复杂度：** 两人同时编辑同一字段时，合并后操作可能使字符级合并（OT/CRDT）更难；但对于字段级 LWW，往往反而更有利。

### 4.2 逻辑批处理（Logical Batching）

“Batch” 是把多个应原子处理的动作打包为一个容器。

- **场景：** “创建任务” + “打标签” + “移动到项目 X”。
- **实现：** 客户端发送单个 `BATCH` 操作，内含子操作数组。
- **收益：** 保证一致性。即使网络中断，也不会出现“任务创建了但标签没加上”。

## 5. 冲突解决策略

### 5.1 冲突检测

- **服务端视角：** “我收到基于 v1 的实体 X 更新，但当前已是 v2。”
- **客户端视角：** “我拉到 `ServerSeq 50` 的 Op A（修改 Task 1），但本地也有待上传的 Op B（同样修改 Task 1）。”

### 5.2 冲突解决模型

1.  **LWW（Last-Write-Wins）：** 简单稳健，但可能丢数据（依赖墙钟时间戳）。
2.  **三方合并：** 若 payload 可 diff（如 JSON Patch），尝试自动合并。
3.  **人工处理：** 标记冲突并让用户选择（UI 复杂）。
4.  **混合策略：** 简单字段用 LWW（Title）、集合用 Merge（Tags）、日志类用 Append（时间追踪）。

## 6. 安全与可靠性

### 6.1 认证

- **Token 机制：** JWT 是主流方案。
- **作用域：** Token 应限制到指定 `user_id` 分区。

### 6.2 加密

- **传输层：** 必须使用 HTTPS/WSS。
- **静态数据：** 若服务端不可信，客户端应先加密 `payload` 再上传。服务端仅同步密文 blob（E2EE）。

### 6.3 限流

- 必须防止单个异常客户端把日志刷爆。

## 7. 总结检查清单

- [ ] **数据库：** SQLite（起步）/ Postgres（扩展）。
- [ ] **ID 生成：** UUID v7（时间有序）。
- [ ] **协议：** HTTP（可靠）+ WebSocket（通知）。
- [ ] **优化：** 高频本地编辑做 coalesce；原子动作做 batch。
- [ ] **冲突：** 服务端负责排序；客户端负责对账与收敛。
- [ ] **安全：** 删除用 tombstone，启动提速用 snapshot。
