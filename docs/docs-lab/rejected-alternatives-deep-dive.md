# 被拒绝的备选方案：深度分析

> 本文档是对 [operation-log-architecture.md](../../docs/sync-and-op-log/operation-log-architecture.md) "Why this architecture: rejected alternatives" 部分的扩展分析。
> 英文文档给出了简要结论，本文档展开每种方案被拒绝的完整技术理由。

---

## 核心约束

操作日志不是偶然复杂度。它是满足以下**硬性、不可妥协约束**的最小设计：

> **在并发多设备编辑时不能静默丢失数据，离线优先，服务器不能合并**
> （WebDAV/Dropbox/LocalFile 没有服务器逻辑；SuperSync 的 payload 是端到端加密的，对服务器不透明）。

任何未来重新设计都必须保留以下性质：

- 并发独立编辑不静默丢失
- 不需要可信/可合并的服务器，且支持不透明的 E2EE payload
- 离线编辑在重连后能干净地 rebase
- 带保留窗口的软删除（tombstone）
- 通过快照 + 压缩实现有界增长
- 冲突元数据宁可误判为并发也不误判为有序（裁剪前先比较时钟）
- 扩展到 1 万+ 活跃 / 2 万+ 归档任务，无主线程 O(N) 操作

## 方案一览

| 备选方案                        | 是什么                                   | 为什么拒绝                                                                                                                                              |
| ------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **全局 LWW（Last-Write-Wins）** | 去掉逻辑时钟，最新的挂钟时间写入胜出     | 用户设备时钟不可靠；并发独立字段编辑互相静默覆盖。仅作为冲突解决中的字段级 tie-break 存活                                                               |
| **Delta / 状态差异同步**        | 保存影子副本，上传变更字段，服务器浅合并 | 影子状态与水印无原子耦合 → 崩溃永久损坏；LWW 浅合并丢失并发独立编辑；O(N) JSON.stringify 在 1 万+ 任务时冻住 UI；需要服务器合并，与不透明 E2EE 不兼容   |
| **全量快照同步**                | 同步整个模型文件（旧版 PFAPI 模型）      | 每次变更都重新传输全部内容；无实体级冲突粒度；无法重构离线编辑的意图。仅作为引导机制（快照 + 尾部重放）保留，不作为同步机制                             |
| **CRDT（Yjs/Automerge 等）**    | 数学保证收敛                             | 概念复杂度高；大多数实现假设可信服务器或中继，与哑文件 + E2EE 约束冲突。op-log 刻意借用 op-based-CRDT 的属性（UUID 幂等性、因果排序），但不引入完整机制 |
| **服务器分配序列号**            | 让服务器施加全序                         | 需要服务器连接才能排序 — 与离线优先和没有服务器的文件型 provider 不兼容。仅作为补充使用（SuperSync seq 用于全局排序；文件型/离线场景仍需向量时钟）      |
| **CR-SQLite**                   | CRDT 嵌入 SQLite 引擎，行/列级自动合并   | SQL ↔ NgRx Store 双写不可行；~22,600 行 NgRx 代码需全部重写；跨版本 schema 迁移复杂度高一个数量级                                                       |

## 1. 全局 LWW（Last-Write-Wins）

### 是什么

整个实体作为一个整体，谁的时间戳大，谁的整个状态覆盖对方。

### 为什么拒绝

**时钟不可靠**：用户设备的系统时钟可能不准确（手动调过、时区错误、电池耗尽后重置）。用挂钟时间做胜负判断，等于把数据正确性建立在一个不可靠的基础设施上。

**并发独立字段编辑互相覆盖**：

```
设备 A: task.title = "做饭"     (时间戳 T1)
设备 B: task.timeEstimate = 60  (时间戳 T2, T2 > T1)
```

全局 LWW → B 赢 → A 改的标题丢失了，用户根本不知道。两个完全不相关的修改，因为碰巧改了同一个实体，就丢了一个。

### 和当前方案的字段级 LWW 有什么区别

| 维度             | 全局 LWW（被拒绝）   | 字段级 LWW（当前方案）       |
| ---------------- | -------------------- | ---------------------------- |
| 使用位置         | 同步层，直接覆盖     | 客户端，冲突解决的最后一步   |
| 前置检测         | 无，直接按时间戳覆盖 | 先用向量时钟判断是否真的冲突 |
| 冲突粒度         | 整个实体             | 单个字段                     |
| 同一实体不同字段 | 丢失一方             | 两个都保留                   |

当前方案中，字段级 LWW 只在向量时钟检测到 CONCURRENT（真正的并发）时才触发。大多数情况下，向量时钟会判断出两个操作是因果顺序的（一个"看见"了另一个），直接应用，不需要 LWW。

## 2. Delta / 状态差异同步

### 是什么

客户端保存一份"影子状态"（上次同步时的快照），每次同步时计算当前状态和影子状态的差异，只上传差异部分。服务器做浅合并（比如同一个字段改了，新的覆盖旧的）。

### 为什么拒绝

**问题 1：崩溃不安全**

```
1. 客户端保存影子状态 snapshot_old
2. 用户改了任务 A → 实际状态变成 snapshot_new
3. 开始同步：计算 diff = snapshot_new - snapshot_old
4. 上传 diff 到一半 → 崩溃了
5. 重启后：实际状态是 snapshot_new，但影子状态还是 snapshot_old
6. 下次同步：diff = snapshot_new - snapshot_old = 重复上次的 diff
```

第 6 步的问题：你不知道 diff 有没有成功上传过。影子状态和"上次成功同步到哪里"之间没有原子绑定，所以你无法区分"已成功"和"未成功"。

op-log 方案不会有这个问题：每条操作有 `syncedAt` 标记 —— 要么标记了（已同步），要么没标记（未同步），存在 IndexedDB 里，崩溃不会丢失。

**问题 2：需要服务器合并**

Delta sync 假设服务器能做"浅合并"。但：

- WebDAV/Dropbox：服务器就是个文件，没有合并逻辑
- SuperSync：payload 是 E2EE 加密的，服务器看到的是密文，不知道"这是 title 字段还是 timeEstimate 字段"

所以服务器不可能做合并，只能客户端自己来。而客户端做合并就需要知道"哪些是并发的、哪些是有因果关系的"，这正是向量时钟干的事。

**问题 3：O(N) 性能差**

diff 同步需要比较两个完整状态快照找出差异。最朴素的做法是每个实体都 `JSON.stringify` 两次 + 字符串比较。1 万个任务，每个任务平均 500 字节 → 每次同步要 stringify 1 万次。在手机上会冻住 UI。

绕过方法（脏标记）理论上存在，但脏标记本身需要持久化，崩溃后可能不一致，又回到了和影子状态一样的原子性问题。op-log 方案天然避免了这个问题：操作本身就是"差异"，不需要 diff。

## 3. 全量快照同步

### 是什么

每次同步上传/下载完整的应用状态文件。旧版 PFAPI 系统就是这种方案。

### 为什么拒绝

**冲突粒度是整个文件**：

```
设备 A：改了任务 1 的标题，上传整个 snapshot_A
设备 B：改了任务 2 的时间，上传整个 snapshot_B
```

服务器收到两个 snapshot，只能选一个。选了 A → 任务 2 的改动丢了。选了 B → 任务 1 的改动丢了。而且因为上传的是整个快照，你甚至不知道丢了什么。

**数据浪费**：改一个任务标题就要上传整个状态文件。

**无法重构意图**：快照只记录"现在是什么"，不记录"用户做了什么"。无法区分"归档了任务"和"删除了任务"。

### 当前方案中的角色

全量快照**没有被完全抛弃** —— 它作为引导机制（bootstrapping）保留：新设备首次同步时下载完整快照 + 重放尾部操作。但日常同步走的是操作日志。

## 4. CRDT（无冲突复制数据类型）

### 是什么

CRDT 是一类数据结构，数学上保证：多个副本独立修改后，只要交换所有修改，最终一定收敛到相同的状态，不需要任何协调。代表库为 Yjs、Automerge。

### 为什么拒绝

#### 4.1 假设可信中继

大多数 CRDT 库的同步层假设有一个中继服务器转发操作。WebDAV/Dropbox 没有这个能力。SuperSync 虽然有服务器，但 payload 是加密的，无法参与 CRDT 协议。

那为什么不能像当前方案一样"下载 → 合并 → 上传"？核心区别在合并逻辑：

- op-log 的合并是**你自己写的**（向量时钟 + LWW），可以控制行为（比如"归档胜出"）
- CRDT 的合并是**库自动做的**，你不能控制它的行为

如果想要"归档胜出"这种自定义规则，你需要覆盖 CRDT 的默认行为，这很困难。

#### 4.2 操作语义丢失

CRDT 只知道"字段值变了"，不知道"用户做了什么操作"。

```
CRDT 收到的：tasksMap.delete(id) + archiveMap.set(id, data) + title 被修改
→ 无法区分"用户归档了项目"和"用户删除了项目然后创建了一个副本"
→ 无法在冲突解决中使用归档优先等语义规则
→ 无法在操作历史中做审计追溯
```

当前方案中，每个 Operation 携带原始 Action 类型（`[Task] Archive`），冲突解决器可以直接读取 `opType === 'MOV'` 触发归档优先。

#### 4.3 与 E2EE 的矛盾

- 若保留 CRDT 的增量同步优势（高频、小包），每个 update binary 都需要独立加密，引入增量包索引、加密顺序保证等额外复杂度
- 若沿用当前的文件级批处理模式，CRDT 的增量同步优势不复存在，但复杂度（Yjs 数据模型 + NgRx 桥接）仍然存在

#### 4.4 SYNC_IMPORT 语义无法表达

`SYNC_IMPORT` 语义为："完全替换当前应用状态，所有并发操作全部丢弃"。CRDT 的 Strong Eventual Consistency 保证"所有操作最终都会合并" —— 与 SYNC_IMPORT 的"有意识地丢弃某些操作"根本对立。

#### 4.5 与 NgRx 的集成成本

CRDT 与 NgRx 有三种集成路径，每种都有不可接受的成本：

**路径一：CRDT + NgRx 双写** — 状态源分裂。NgRx dispatch 和 Yjs `set()` 不是原子操作，崩溃后两个数据源不一致。16 个 meta-reducer 的级联逻辑在 CRDT 环境中失去操作语义。Selector 的引用相等性断链导致 UI 全量重渲染。

**路径二：CRDT 替代 NgRx** — ~22,600 行 NgRx 代码需全部重写或废弃，估算 44-69 人天（约 2-3.5 人月）。失去 DevTools 时间旅行调试、Selector 自动记忆化、EntityAdapter 标准化 CRUD。

**路径三：CRDT + 非 Angular** — 直接否决。Angular 是跨平台需求驱动的既定技术栈，优先级高于同步方案选型。

### 当前方案借用了什么

| CRDT 属性                              | op-log 中的对应                                            |
| -------------------------------------- | ---------------------------------------------------------- |
| 操作幂等性（同一操作应用两次效果不变） | 操作有 UUID，重复应用会被跳过                              |
| 因果排序（知道哪个操作在先）           | 向量时钟                                                   |
| 操作交换性（顺序无关）                 | 不完全具备 —— 有些操作顺序敏感（如列表排序），需要冲突检测 |

当前方案的本质是：借鉴 CRDT 的核心思想，但自己控制合并逻辑。

## 5. 服务器分配序列号

### 是什么

让服务器给每个操作分配一个全局递增的序号：操作 1, 操作 2, 操作 3…… 所有客户端按序号顺序应用，天然有序。

### 为什么拒绝

1. **离线时无法获取序号**：用户在飞机上改了 10 个任务，这些操作没有序号。等联网了再分配？那离线期间怎么排序？
2. **文件型同步没有服务器**：WebDAV 就是个文件，Dropbox 就是个网盘，它们没有"给操作编号"的能力。

### 当前怎么用

SuperSync（自建服务器）**补充**使用序列号：服务器收到操作后分配 `serverSeq`，客户端下载时按 `serverSeq` 排序。但向量时钟仍然存在，因为首次同步或离线重连时需要向量时钟判断因果关系，文件型同步完全没有序列号。

## 6. CR-SQLite

### 是什么

将 CRDT 机制嵌入 SQLite 数据库引擎（代表库：vlcn.io / CR-SQLite、PowerSync），在存储层实现行/列级自动冲突合并。数据以 SQL 表结构组织，变更集作为文件通过网盘同步。

### 为什么拒绝

#### 6.1 SQL ↔ NgRx Store 双写不可行

CR-SQLite 要求数据以 SQL 表形式存储于 SQLite 中，NgRx Store 以内存中 JavaScript 对象形式持有数据。两者并行导致状态源分裂：

- SQLite 的事务不保护 NgRx Store。若 store.dispatch 中的 Reducer 执行成功但 meta-reducer 级联失败，SQLite 已是新状态，NgRx Store 可能在错误的中间状态
- NgRx 的 `createSelector` 以 Store State 切片为输入，SQL 查询没有自动重算机制

#### 6.2 替代 NgRx 的成本

与 CRDT 替代 NgRx 类似：~22,600 行代码需全部重写。16 个 meta-reducer 的级联逻辑需从 NgRx 生态迁移到 SQL 触发器或应用层事务，这不仅是代码迁移，更是架构重构。

#### 6.3 跨版本 Schema 迁移复杂度

操作日志方案中新增字段的 schema 迁移只需处理 JSON 字段映射。CR-SQLite 方案需要 DDL 迁移脚本，且两个设备的 schema 版本不一致时，未执行迁移的设备收到包含新列的变更集将无法合并 —— 必须实现 schema 版本协商协议，比 JSON 层面的字段映射复杂一个数量级。

#### 6.4 唯一优势场景的低收益

CR-SQLite 相对当前方案的唯一优势是列级合并（同实体不同字段并发）。但在实际使用中，超过 95% 的并发操作发生在不同任务之间，而非同一任务的不同字段。为此边际收益引入完整 CR-SQLite 技术栈不划算。

## 7. 第三方云数据库 / BaaS

### 是什么

依托 Firebase Firestore、Supabase、RxDB + CouchDB 等成熟云服务的离线缓存与多端并发同步能力。应用通过 SDK 操作数据，SDK 自动管理离线缓存与增量同步。

### 为什么拒绝

**一票否决：数据主权与隐私原则的不可调和矛盾。**

Super Productivity 的核心产品定位是"隐私优先的离线应用"。BaaS 方案要求将所有用户的 Todo、笔记、项目、时间追踪数据存储在第三方服务器上，直接违反了这一核心承诺。

补充否决因素：

- **供应商锁定**：用户数据完全依赖第三方服务，无法迁移到其他网盘或本地存储
- **费用不可控**：Firebase 免费方案对重度用户可能不足，集中式付费服务模式对开源项目不可持续
- **多后端策略不可行**：项目需要同时支持 6 个同步后端让用户自由选择，BaaS 强制所有数据流向单一云服务

## 8. 并发时会不会丢数据？

当前方案**不是零丢失**，而是把丢数据的场景限制到了最小且可控的范围内。

### 已知会丢失的（有意设计）

1. **LWW 冲突解决**：两个设备并发改了同一个实体的同一个字段，LWW 覆盖一方。但这是在向量时钟检测到冲突之后的解决策略，用户会收到通知。
2. **归档胜出**：设备 A 归档了任务，设备 B 同时改了标题。B 的改动被丢弃。归档代表明确的用户意图，不应被并发字段修改"复活"。
3. **SYNC_IMPORT 覆盖**：用户主动恢复到某个时间点，意味着"我不关心之后的改动"。

### 不会丢失的

- 两个设备改了同一实体的不同字段 → 向量时钟检测到并发 → 字段级合并 → 两个改动都保留
- 两个设备改了不同实体 → 根本不会冲突

### sync window 的理论风险

同步窗口期间，如果一个 selector-based effect 读到了旧的 state 并产生了操作，这个操作可能基于错误的前提。`skipDuringSyncWindow()` 防止这类 effect 在同步窗口期间执行。

### 向量时钟裁剪的理论风险

`MAX_VECTOR_CLOCK_SIZE = 20`。20+ 不同设备同时活跃且频繁分叉的场景下，裁剪后可能误判因果关系。实际上这种场景极少。

### 服务器确认的理论风险

服务器返回 200 成功但实际没持久化（进程崩溃）。客户端标记了 `syncedAt` 但服务器没有这条操作。这个漏洞在所有分布式方案中都存在，不是 op-log 特有的问题。
